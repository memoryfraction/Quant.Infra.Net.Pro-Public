## Phase 1 Task B (site) progress #4 — Playwright verification + the stats shape bug

Two suites are now green. `node planner/tests/run.js` => **1125 passed, 0 failed** (baseline 199) and
`scripts/verify-site.js` => **131 passed, 0 failed** (14 browser sections). Getting there exposed one
severe product bug and three harness bugs.

**Real bug #6 (severe): `stats/stats.js` crashed against the worker's real response.**
`distRows()` called `rows.reduce(...)` on whatever `show()` handed it and read `r.key`, but the worker
returns five different distribution shapes. The result: 8 of the 10 spec-mandated blocks never rendered.

| # | Shape | Where | Symptom |
|---|-------|-------|---------|
| a | `[{v, n}]` (aliased `v`) | `profiles.age_band`/`asset_band`/`goal`/`leverage_exp` | labels became `(空)` **and** `rows.reduce is not a function` threw, aborting `show()` right after block ② |
| b | `[{s, n}]` / `[{c, n}]` | `utm.source`/`medium`/`campaign`, `campaigns` | every row silently rendered `—` (no exception, so tests stayed green) |
| c | `[["A", 3]]` (`Object.entries`) | `profiles.markets`/`follows`, `wtp` via `countOptions()` | `r.key`/`r.n` both `undefined` -> `(空) 0 —` |
| d | `[{device, n}]` etc. | `devices`/`os`/`browsers` (unaliased selects) | labels blank |
| e | `avg_s` (already seconds) | `engagement` (block ⑤) | read `avg_dur_ms`, always `—`; dividing by 1000 would have been doubly wrong |
| f | `{numeric:{k:{p25,med,p75,n}}, categorical:{k:[[v,n]]}}` | `calcs.inputs` (block ⑥) | read `.median` / `.kind` / `.values`, so nothing rendered |

Fix: a single `distList(rows, col)` normaliser that accepts `{key,n}` / `{v,n}` / `{name,n}` /
`["值", n]` / bare `{<col>, n}`, with `Array.isArray` guards so a malformed field degrades to an empty
table instead of killing the whole dashboard; `distRows(rows, total, col)` takes the column hint; blocks
⑤ and ⑥ were rewritten against the worker's real field names.

**Root cause of the miss** matters more than the fix: `planner/tests/stats.test.js`'s fixture had been
hand-shaped to match the *renderer* (`{key,n}`, `avg_dur_ms`, `median`, `kind:"select"`) rather than the
*worker*, so it passed while production was broken. The fixture now documents that it mirrors
`src/index.js` L459 / L468 / L469-471 / L474-477 / L486-491 / L549-550, and carries 13 new
shape-regression assertions (including `no value rendered as [object Object]` and `no row degraded to an
empty label`). `scripts/verify-site.js` section 11 had the same flaw — its payload was entirely fictional
(`sessions:{sids:44}`, `devices:{mobile:70}`, `uniques:{vids,ips}`, `cohorts:[{day,size}]`) — and is now
shaped like the real response with all 10 blocks asserted.

**Three harness bugs fixed (the product was correct in each case):**
1. Share-URL capture. Headless HTTP is not a secure context, so `navigator.clipboard` is absent and
   `legacyCopy()` writes the link into a *transient* `<textarea>` that it selects and then removes —
   wrapping `execCommand` runs too late to see it. Now hooks `HTMLTextAreaElement.prototype.select`.
   The real produced URL confirms the feature works: `?s=eyJhMCI6MCwiY3VycmVudCI6MTAwMDAwLCJleHBlbnNlTm93IjoxMjM0NTY3…&from=share`
   (the encoded inputs include the value typed into the form).
2. Third-party error attribution. `counter.dev` throws the *same* `"storage blocked"` message our code
   would under blocked storage, so filtering by message hid whose bug it was. The harness now records
   stacks and filters by origin.
3. Share-button click. The button sits far below the fold; a synthetic DOM click replaces
   `locator.click()` for this link-generation assertion.

**Running Playwright here has one gotcha:** it is installed at

## Phase 1 — DEPLOY + ONLINE SMOKE, and two worker bugs found only in production (2026-10-12 ~23:00 ET)

Deployed `awl-analytics` to Cloudflare (version `487c6097`, route `www.alpha-wealth-lab.com/api/*`)
with D1 migrations 0002/0003 applied remotely and all three secrets set (`IP_SALT`, `STATS_TOKEN`,
`BREVO_API_KEY`). Then smoke-tested every endpoint against the live database.

**The smoke test's real value was not the 204s — it was checking whether the data actually landed.**
Every write endpoint answered `204 OK`, which on its own reads as success. Two of them were lying.

### Bug #7 — `POST /api/hit` wrote nothing, ever (SEVERE)

The endpoint's INSERT listed **28 columns but supplied only 27 `?` placeholders**, so real D1 raised
`SQLITE_ERROR` on every single write. The rejection was drained with `.catch(() => {})`, which meant:

- the endpoint still answered `204`, so clients saw success;
- `wrangler tail` showed nothing, so operators saw success;
- the dashboard just showed no new data — indistinguishable from "nobody visited yet".

Evidence that settled it: five valid hits in a row, each returning 204, while
`SELECT COUNT(*) FROM hits` sat unchanged at 212 before and after. The D1 result arrived only after
a *manual* INSERT (using the identical 28-column list) succeeded, which proved the schema and the
column names were fine and pushed the fault back into the worker's own statement.

Fix: the missing 28th placeholder, plus replacing the silent catch with a payload-free
`console.error("hit_insert_failed", e.message)`. The original `.catch(() => {})` is what let a total
collection outage masquerade as a healthy service, so removing it is the more important half.

### Bug #8 — `GET /api/admin/subscribers` returned 500 when unfiltered

The statement conditionally gained a `WHERE status=?`, but `.bind()` was called **unconditionally**.
With no `?status=` filter that bound 1 value to a statement containing 0 placeholders, which D1
rejects (error code 1101). The `?status=confirmed` path worked, so the endpoint looked fine unless
you happened to call it the normal way.

Fix: bind only when the clause is actually present.

### Why 62 green tests missed both

The in-memory D1 stub in `test/index.test.mjs` accepted **any** `bind()` arity. It mapped `args[i]`
onto columns by position and never once compared counts, so it was strictly more permissive than the
real service. A stub that tolerates what production rejects converts production failures into green
tests.

The stub now enforces the invariant from both sides — INSERT column count vs placeholder count, and
`bind()` value count vs placeholder count — and I proved the assertions actually bite by re-injecting
each defect and confirming precise failures:

```
INSERT INTO hits: 28 columns but 27 placeholders
bind() arity mismatch: statement has 0 placeholder(s) but 1 value(s) bound
```

Both bugs are now covered by tests that fail loudly if the pattern returns.

A fresh hit writes a complete row (id 213/214/215) with `device`/`os`/`browser` parsed from the UA,
`utm_*` preserved, and `ip_hash` as a 16-hex HMAC; `/api/stats` reflects it immediately; the full

- `/api/hit` uses short keys (`e`,`p`,`r`,`v`,`d`,`sc`), and whitelists are exact — an unknown event

## Phase 1 — bug #9 fixed, redeployed, and re-verified live

Third production-only defect, same family as #7 and #8 (a statement/guard whose shape does not match
reality). Found by the post-deploy smoke test, not by the suite.

### The defect — `POST /api/profile` 500s on an out-of-whitelist enum

`handleProfile` guarded its four enum fields with `x !== undefined`:

```js
age_band: has("age_band") && age !== undefined ? age : base.age_band,
```

but `cleanEnum` returns **`null`**, not `undefined`, for a value outside the whitelist. The test was
therefore *always true*, so a rejected enum was written to the column as SQL NULL and tripped
`NOT NULL constraint failed: profiles.age_band`, turning the whole request into a 500 — when the spec
only requires that an invalid value be **silently dropped**.

The trap that exposed it: I sent `age_band:"35-44"` as throwaway "bad test data". It is not in
`AGE_BANDS` (`<30,30-39,40-49,50-59,60+`), so my malformed request surfaced a genuine defect.
Found via `wrangler tail`: `[ERROR] Error: D1_ERROR: NOT NULL constraint failed: profiles.age_band:
SQLITE_CONSTRAINT` at `handleProfile (index.js:508:3)`.

### The fix — two independent guards, both proven load-bearing

```js
const base = existing || { age_band: "", asset_band: "", goal: "", markets: "", follows: "", leverage_exp: "", country: "" };
const keep = (raw, cleaned) => (has(raw) && cleaned !== null ? cleaned : undefined);
const rec = {
  lang,
  age_band: keep("age_band", age) ?? base.age_band,
  asset_band: keep("asset_band", asset) ?? base.asset_band,
  goal: keep("goal", goal) ?? base.goal,
  markets: has("markets") ? markets : base.markets,
  follows: has("follows") ? follows : base.follows,
  leverage_exp: keep("leverage_exp", lev) ?? base.leverage_exp,
  country,
};
```

Ablation, run in both directions to be sure neither guard was decorative:

| variant | result |
| --- | --- |
| both guards (shipped) | 42 pass / 0 fail |
| drop `keep`, keep `??` fallback | 39 pass / **3 fail** — `NOT NULL constraint failed: profiles.asset_band` + `age_band` |
| keep `keep`, drop `??` fallback | 39 pass / **3 fail** — same two errors |

Removing *either* guard alone reproduces every failure, so the double protection is real and not
one guard masking a broken other. (A first, sloppier injection deleted only the `keep` definition
while leaving a usage behind, which produced a `ReferenceError: keep is not defined` rather than the
NOT NULL error — a narrower injection was required to isolate the fallback.)

### The stub was the reason all three bugs passed

`test/index.test.mjs`'s in-memory D1 was strictly **more permissive** than real D1: it accepted any
`bind()` arity and modelled no NOT NULL constraints. It now enforces:

- INSERT column count vs `?` placeholder count
- `bind()` value count vs placeholder count, **both** directions
- NOT NULL for every column declared so in migrations 0002 + 0003

Each guard was proven by re-injecting the corresponding bug and confirming a precise red message
("28 columns but 27 placeholders" / "0 placeholder(s) but 1 value(s) bound" /
"D1_ERROR: NOT NULL constraint failed: profiles.age_band").

One pre-existing assertion had **encoded bug #9 as correct behaviour**:

```js
assert.equal(p.asset_band, null, "illegal enum dropped (stored as NULL/empty)");
```

The `null` that assertion demanded is exactly what production rejects. It now requires `""` and adds
`assert.notEqual(p.asset_band, null, ...)`. Three new regression tests were added; suite is
**42 pass, 0 fail** (the earlier "62" figure in this log was a miscount of the same 42 tests).

### The testing trap that nearly produced a false "still broken"

After deploying I re-sent the failing payload with plain `curl` and got **204**, then queried D1 and
found `profiles` still at **0 rows** — a silent write failure, the same signature as bug #7. It was
not. `BOT_RE` in `src/lib.js` matches `curl`, and every write handler opens with
`if (isBot(request.headers.get("User-Agent") || "")) return noStore();`. Every probe was being
discarded as a bot, returning 204 with nothing written — byte-identical to success.

With a browser User-Agent the picture is unambiguous, and the row confirms the fix:

```
vid=pc6f4d1b2a3e5f7c9  lang=en  age_band=""  asset_band=""  goal="retire"  leverage_exp=""
age_null=0  asset_null=0
```

Invalid enums dropped to empty strings (not NULL), while the valid field in the same request was
still applied. The don't-clobber path was verified separately: a stored `age_band:"40-49"` survives a
later `age_band:"nonsense"` update unchanged.

**Rule for future smoke tests: always pass a browser UA to write endpoints, and never trust the
status code alone — confirm the row with a D1 SELECT.**
